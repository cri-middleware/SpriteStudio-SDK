# 実装フェーズ 1：初期化 (Initialization)

Player の基本機能の実装において、初期化時に行うべき処理と、メモリ管理の戦略について記載します。

## 1. libssruntime の初期化
まず、libssruntime の各機能を利用するためのコンテキストを作成します。通常、1 つの Player インスタンス（または 1 つのアニメーションオブジェクト）につき 1 つのコンテキストを保持します。

```cpp
// コンテキストの作成
void* context = ss_runtime_create();
```

## 2. ssab ファイルのロードと libssruntime への渡し方
ネイティブライブラリである libssruntime へ ssab データを渡す方法は、利用するプログラミング言語のポインタ操作能力に応じて 3 つの運用パターンがあります。

### パターン A：ポインタを直接渡せる場合（推奨）
- **対象言語:** C++, C# (unsafe) など
- **運用:** ssab データのオーナー（メモリ管理責任者）は Player 側になります。
- **実装:** `ss_runtime_load_ssab_borrow` を使用します。
- **メリット:** メモリコピーが発生せず、最も効率的です。

### パターン B：ポインタ経由で参照のみ可能な場合
- **対象言語:** Kotlin, TypeScript(JavaScript) など
- **運用:** ssab データのオーナーを libssruntime 側に移譲します。Player はライブラリが所有するデータを参照して利用します。
- **実装:** 
    1. `ss_runtime_load_ssab_copy` を実行してデータをライブラリ側にコピーします。
    2. コピー完了後、Player 側の元のデータは解放します。
    3. `ss_runtime_get_ssab` を実行し、ライブラリ側が管理しているポインタを取得して、パース等に利用します。

### パターン C：ポインタの受け渡しが困難な場合
- **対象言語:** 一部の高レベル言語
- **運用:** Player 側と libssruntime の両方が ssab データのコピーを保持します。
- **実装:** `ss_runtime_load_ssab_copy` を実行し、Player 側でも同じデータを保持し続けます。
- **デメリット:** メモリ消費が 2 倍になるため、可能な限り避けてください。

## 3. アセット（テクスチャ）のロードと紐付け
ssab 内には「どのセルマップ（画像）を使用するか」という情報が含まれています。Player はこれらをエンジンのリソースとしてロードし、管理する必要があります。

- **セルマップ情報の取得:** `ssab->cellmaps()` をループして、必要な画像パスを取得します。
- **エンジンのテクスチャとの紐付け:** ロードしたエンジンのテクスチャオブジェクトと、ssab 内の CellMap ID を対応させるマップ（Dictionary等）を作成します。
- **Cell ID からの引き当て:** 描画時、`PartState` から得られる Cell ID を元に、どのテクスチャのどの領域（UV）を描画すべきかを即座に引ける仕組みを用意してください。

## 4. 再生するアニメーション情報の管理
ssab データには複数のアニメーションが格納されている場合があります。Player はこれらの一覧を取得し、外部からアニメーションを選択して再生できるような API を提供する必要があります。

```cpp
// ssab 内のアニメーション名一覧を取得する例
if (ssab->animations()) {
    for (auto anime : *ssab->animations()) {
        std::string name = anime->name()->str();
        // この名前を Player の外部 API（Play("name") など）で利用できるようにする
    }
}
```

## 5. 後処理（インスタンス破棄時）
メモリリークを防ぐため、Player の破棄時には必ずコンテキストを解放してください。

```cpp
// コンテキストの破棄
ss_runtime_destroy(context);
```
