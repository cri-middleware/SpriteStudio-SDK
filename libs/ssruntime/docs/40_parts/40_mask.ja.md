# マスク

SpriteStudio の「マスク」と「クリッピング」の実装方法です。2 つはステンシルという同じ仕組みで実現しますが、**機能としては別物**です。Brain は描画の順番とマスクの DrawBatch を渡し、どのパーツがどのマスクの影響を受けるかの判定と、ステンシル（または被覆ビットマップ）への書き込みは Player が行います。

- §1〜§2 は、エンジンによらない判定の規則です。
- §3 は、FrameData から何を読むかです。
- §4 は GPU のステンシルを使う実装、§5 はステンシルを使えないエンジンでの実装です。どちらか一方を選びます。

---

## 1. 概念とパーツの役割

### 1-1. 用語

| 用語 / フィールド | 読む場所 | 意味 |
|---|---|---|
| **マスクパーツ** `PartTypeMask` | PartData（静的） | マスク専用のパーツの種類。常に純粋なマスク（色を描かない） |
| **マスク**（機能） | — | 自分より描画優先度が **低い** パーツを、形の **外側** に残す |
| **クリッピング**（機能） | — | 自分より描画優先度が **高い** パーツを、形の **内側** に収める |
| **writer** | — | ステンシルに書くパーツ（純粋なマスクか、クリッピング） |
| **対象** | — | マスクやクリッピングの影響を受ける描画パーツ |
| **純粋なマスク** | — | 色を描かず、形だけを書く writer（マスクパーツと、マスクにした描画パーツ） |
| `Priority` | **FrameData（毎フレーム）** | 描画優先度（`PartState.priority`）。同じ値ならパーツの ID で決まる（§2-1） |
| `mask`（float、`0..255`） | **FrameData（毎フレーム）** | カットアウトの閾値を兼ねる。`0` で writer を無効にする（§2-2 / §2-5） |
| `mask_influence` | **PartData（静的）** | **役割によって意味が変わる**（§1-3）。書き込み方か、マスクを受けるかの印 |
| `mask_write` | **PartData（静的）** | 描画パーツを **クリッピング** の writer にする印 |
| `draw_as_mask` | **PartData（静的）** | 描画パーツ（シェイプ / テキスト / 9 スライス）を **純粋なマスク** にする印。作画では種類ごとの設定だが、ssab では 1 つにまとまっている |
| `visible_inside_mask` | **PartData（静的）** | 極性。`1` = 内側に描く / `0` = 外側に描く（§2-4） |
| `Hide` | **FrameData（毎フレーム）** | 非表示（`PartState.hide`）。**writer では Player も判定する**（§3） |

マスクに関わるフィールドは、2 つの表に分かれています。どちらから読むかを取り違えないでください。

- **PartData（ssab のパーツ定義）**: `mask_influence` / `mask_write` / `visible_inside_mask` / `draw_as_mask` / パーツの種類。**一度読めば変わりません。**
- **FrameData（毎フレーム）**: `mask` / `Priority` / `Hide` / パーツカラー / 不透明度。**毎フレーム読み直します。**

以降の擬似コードでは、`part.data.*`（PartData）と `part.frame.*`（FrameData）で出どころを区別します。

### 1-2. マスクとクリッピングは別の機能

使い道は似ていて、仕組みも同じですが、機能としては別物です。

| | **マスク** | **クリッピング** |
|---|---|---|
| 持つパーツ | **マスクパーツ** | 描画パーツ（通常 / メッシュ / シェイプなど） |
| 自分の色 | **描かない**（形だけを書く） | **描く**（自分を描きながらステンシルにも書く） |
| 効く相手 | 自分より **描画優先度が低い** 描画パーツ | 自分より **描画優先度が高い** 描画パーツ |
| よくある見え方 | 形の **外側** を残す | 形の **内側** に収める |

マスクは専用のパーツが持つ機能、クリッピングは描画パーツが付け加えて持つ機能、という非対称な関係です。

### 1-3. パーツの役割と `mask_influence`

パーツの役割は、「writer か」「対象か」で決まります。マスクの機能を持つのはマスクパーツだけですが、一部の描画パーツは `draw_as_mask` で **マスクパーツと同じ役割**（純粋なマスク）になれます。

| パーツの種類 | 既定の役割 | 純粋なマスクになる条件 | クリッピング（`mask_write`）を持てるか |
|---|---|---|---|
| **マスク**（`PartTypeMask`） | 常に純粋なマスク | （常に） | — |
| **通常** | 描画 | （なれない） | ○ |
| **メッシュ** | 描画 | （なれない） | ○ |
| **シェイプ** | 描画 | `draw_as_mask == 1` | ○（`draw_as_mask == 0` のとき） |
| **テキスト** | 描画 | `draw_as_mask == 1` | ○（`draw_as_mask == 0` のとき） |
| **9 スライス** | 描画 | `draw_as_mask == 1` | ○（`draw_as_mask == 0` のとき） |

- **シェイプ**: マスクにしたシェイプはテクスチャを持たないので、カットアウトの閾値（§2-5）が効かず、**図形全体がマスク**になります。
- **テキスト**: 文字は Player が描くので、Brain にはマスクの形を書く材料がありません。`draw_as_mask == 1` のテキストパーツは**描画計画から除外され**、マスクとしても描画としても働きません。通常のテキストパーツ（`draw_as_mask == 0`）がマスクの対象として切り取られるかは、Player のテキストの描き方しだいです。

Player での役割の判定は、次の 3 つの式になります。

```
pure_mask   = PartTypeMask || draw_as_mask
is_writer   = pure_mask || mask_write          // ステンシルに書くすべてのパーツ
is_clipping = mask_write && !pure_mask         // 色も描く（描画優先度の高い側に効く）
```

#### `mask_influence` は役割によって意味が変わる

`mask_influence` は 1 つのフィールドですが、パーツの **役割によって意味が変わります**。

| 役割 | `mask_influence` の意味 |
|---|---|
| **マスクパーツ**（writer だけ） | **書き込み方**。`0` = 加算 / `1` = 反転（§2-3） |
| **描画パーツ**（writer でない対象） | **マスクを受けるかの印**。`1` = 受ける / `0` = 受けない（§2-2） |
| **クリッピング**（writer であり描画パーツでもある） | 上の **両方を同時に兼ねる**。同じ値が、書き込み方と、マスクを受けるかの印の両方として使われる |

たとえば `mask_influence == 1` のクリッピングは、次の 2 つが同時に成り立ちます。

- **受ける印 = 1**: 自分も他のマスクの影響を受ける
- **書き込み方 = 反転**: 自分がステンシルに書くときは反転で書く

これは同じフィールドを意図して兼ねさせている仕様です。Player で値を分けたり、片方の意味を捨てたりしないでください。

## 2. 判定の規則

マスクとクリッピングは機能が違いますが、どちらも次の規則で一様に扱えます。

### 2-1. スコープ（どの描画パーツにマスクが及ぶか）

描画優先度で決まります。

- **マスク** → 自分より **描画優先度が低い** 描画パーツに効く。自分より描画優先度が高くなったパーツには効かない
- **クリッピング** → 自分より **描画優先度が高い** 描画パーツに効く。描画の最後まで続く。インスタンスの中で書かれたものは、インスタンスを越えて描画全体の最後まで続く（§2-7）

描画優先度は、原則として FrameData の `Priority` で決まり、同じ値ならパーツの ID（格納順のインデックス）が大きいほうが上（描画優先度が高い）です。

実装では、`draw_order`（描画優先度の低い順に並んだパーツの列）の中の位置 rank で判定します。writer の rank を `M`（マスク）/ `C`（クリッピング）とすると、

- マスク: `rank < M` のパーツに効く
- クリッピング: `rank > C` のパーツに効く

### 2-2. マスクを無効にする条件

writer が働くのは、次の **両方** を満たすときだけです。

- **`mask != 0`**（`mask == 0` なら何も書かない）
- **`Hide == false`**（`Hide == true` なら何も書かない）

描画パーツがマスクの影響を受けるのは、**`mask_influence == 1` のときだけ**です。`mask_influence == 0` の描画パーツは、マスクもクリッピングも受けません。

**`mask_write` はこの判定に関わりません。** クリッピング（`mask_write` を持つ描画パーツ）でも、**自分の色が他のマスクで切り取られるかは、自分の `mask_influence` だけ**で決まります。自分が書くマスクで自分の色を切り取らないでください（先に描いてから書きます）。`mask_write` が決めるのは、どのパーツが書くか（§1-3）だけです。

無効になった writer（`mask == 0` か `Hide == true`）は、writer が無いのと同じです。

### 2-3. ステンシルへの書き込み方（OP）

- **マスクパーツ**: `mask_influence` が書き込み方を兼ねます。`0` = **加算**（`stencil + 1`）/ `1` = **反転**（`~stencil`）
- **クリッピング**: 同じく `mask_influence` が書き込み方を兼ねます（マスクパーツと同じ解釈）。クリッピングは描画パーツでもあるので、**同じ値が「受ける印」（§2-2）と「書き込み方」の両方**として使われます（§1-3）

### 2-4. 極性（マスクの内側と外側のどちらに描くか）

極性は、**機能ではなく、対象パーツの `visible_inside_mask`** だけで決まります。

- `visible_inside_mask == 1` → マスクの **内側** に描く
- `visible_inside_mask == 0` → マスクの **外側** に描く
- 判定: `masked == visible_inside`（真なら描き、偽なら `discard`）

したがって、内側に描く対象（マスクを受け、実効の `visible_inside_mask` が `1`）は、**それを覆うマスクが無いところでは描かれません。アニメーションにマスクが 1 つも無い場合**や、writer がすべて無効な場合も同じです。マスクするものが無いからといって、この対象の判定を省かないでください。対象を隠すのは、その判定です。

§1-2 の「マスクは外側、クリッピングは内側」は **作画でよく使う既定値** で、極性そのものは対象の設定です。**対象がマスクとクリッピングの両方のスコープに入る場合も、1 つのステンシルと、対象の 1 つの `visible_inside_mask` で判定します**（機能ごとに極性を分けません）。

### 2-5. カットアウトの閾値

マスクとクリッピングで **共通** に、FrameData の `mask`（`0..255`）から、ステンシルに書く画素を決めます。シェーダで処理します。

- 閾値 = `(255 - mask) / 255`。テクスチャのアルファが閾値を超える画素だけを書く
- `mask == 255` → 閾値 0 → **完全に透明（α = 0）でないすべての画素**を書く
- `mask == 0` → 閾値 1.0 → どの画素も書かない（§2-2 と一致）

**テクスチャを持たないシェイプ**には閾値が効かず、図形全体を書きます。

### 2-6. インスタンスを通したマスクの設定の合成

対象が **インスタンスパーツ** の場合、マスクは **その子アニメーション全体** に及びます。このとき、インスタンスパーツ（呼び出す側）の設定と、子アニメーションの各パーツ（呼び出される側）の設定は **合成** されます。どちらか一方が勝つのではありません。

| 設定 | 合成 | 意味 |
|---|---|---|
| `visible_inside_mask` | **OR** | インスタンスパーツが「内側」を求めたら、その子アニメーションのパーツはすべて内側に描く |
| `mask_influence` | **AND** | インスタンスパーツがマスクを受けないなら、その子アニメーションのパーツはすべてマスクを受けない |

実効値は次のとおりです。

```
実効 influence      = インスタンスパーツの mask_influence      && 自分の mask_influence
実効 visible_inside = インスタンスパーツの visible_inside_mask || 自分の visible_inside_mask
```

- **合成は 1 段にしか及びません。** 使うのはインスタンスパーツ自身の値で、インスタンスパーツがさらに上から受け取った値ではありません。子アニメーションの中にあるインスタンスのパーツは、**そのインスタンスパーツ**とだけ合成し、それより上とは合成しません。たとえば、最上位のアニメーションのインスタンスパーツが `mask_influence == 0` のとき、子アニメーション自身のパーツはマスクを受けませんが、その中にあるインスタンスのうち、インスタンスパーツが `mask_influence == 1` のもののパーツは、マスクで切り取られます。
- **合成は、上でマスクしているかどうかによりません。** 呼び出す側のアニメーションが自分のマスクを持たなくても合成します。
- **どのインスタンスからも呼ばれていない最上位のアニメーション**は、`mask_influence = 1` / `visible_inside_mask = 0` と合成するので、各パーツは自分の設定どおりに判定されます。
- **スコープ**（§2-1）は、子アニメーションがインスタンスパーツの位置に描かれるものとして、描画全体の順番で決まります。呼び出す側のマスクは、インスタンスパーツに及ぶところで子のパーツにも及び、子アニメーションの中のマスクは、子自身の rank で子自身のパーツに効きます（§2-7）。合成が効くのは、**受けるかどうか（§2-2）と極性（§2-4）** です。
- **`mask_write` は合成しません。** そのパーツ自身が書くという局所的な事実です。

子を独立して組み立てる構造の Player では、**子を組み立てる直前に、インスタンスパーツの値を子へ渡す**のが素直です。親自身が受け取った値は渡しません。階層全体で合成する（すべての段を AND / OR でつなぐ）扱いも、呼び出す側がマスクしているときだけ合成する扱いも、SpriteStudio と食い違います。「子が自分の設定を持てば子が勝ち、持たなければ親を引き継ぐ」のような、OR でも AND でもない扱いも同様です。

### 2-7. インスタンスの中で書かれたクリッピングの持ち越し

§2-6 は、マスクが外からインスタンスへ及ぶ **下り方向** の合成でした。子アニメーションの中で書かれたマスク（純粋なマスクもクリッピングも）は、まず **その子アニメーション自身のパーツ** に、ふつうのアニメーションと同じ §2-1 の規則で、外から及ぶマスクと合わせて効きます。さらに逆向きに、**子アニメーションの中で書かれたマスクが、その外側（親アニメーションで、そのインスタンスより後に描かれるパーツ）に及ぶ** **上り方向** の持ち越しもあります。

- **持ち越すのはクリッピング（`mask_write` の描画パーツ）だけ**です。純粋なマスクは自分の rank で打ち消されて子アニメーションの中で閉じる（§2-1 / §4-2）ので、境界を越えません。クリッピングは「自分より後のパーツに、アニメーションの描画の最後まで効く」（§2-1）ので、**その「最後」がインスタンスの境界ではなく、親アニメーションの描画の最後まで延びる**と考えてください。
- **閉じる処理（打ち消し / 戻し）は、親アニメーションの描画がすべて終わるまで遅らせます。** インスタンスが入れ子なら、さらに上の親へ送ります。
- **スコープ**: 持ち越したクリッピングは、**親の `draw_order` の中でのインスタンスパーツの rank** を基準に、それより後（`rank > インスタンスの rank`）の親のパーツに効きます（§2-1 のクリッピングのスコープを、インスタンスパーツの位置で判定する）。
- **書き込み方**: 子アニメーションの中の writer の書き込み方（§2-3 の加算 / 反転）は、**実効 `mask_influence`（自分の `mask_influence` && インスタンスパーツの `mask_influence`）** で決めます（§2-6 と同じ 1 段の合成）。インスタンスパーツが `mask_influence == 0` なら実効値は 0 になり、その writer は **加算（カウンタ）の側 = 和集合** に入ります（反転の側には入りません）。これで、外側の別のマスクと `mask_influence` が違う場合も、**打ち消し合わず和集合** になります（§4-4 の 2 つのプレーンの分離と一致します）。
- **対象の側（親の後続のパーツ）**: 親自身が writer を 1 つも持たなくても、表示中のインスタンスが開いたままのクリッピングを残していれば、**インスタンスより後の親のパーツをマスクの対象** として扱う必要があります。

純粋なマスクが持ち越されず、クリッピングだけが持ち越されるのは、両者のスコープ（§2-1）の違いによります。純粋なマスクは「自分より前」で完結して自分の rank で閉じますが、クリッピングは「自分より後、アニメーションの最後まで」で、その最後がインスタンスの境界を越えて親の最後まで延びるためです。

## 3. FrameData から読むもの

**マスクの DrawBatch（`DrawBatchKind::Mask`）が出るパーツ**（どれも `count = 1`、`vertex_count` / `index_count` は `0`）:

- **マスクパーツ**（`PartTypeMask`）
- **`draw_as_mask` でマスクにした描画パーツ**（シェイプ / 9 スライス）。マスクの DrawBatch と自分の色の DrawBatch が **同じ rank に両方** 出ます。純粋なマスクは色を描かないので、**色の DrawBatch は描かないでください。** この組のマスクの DrawBatch は、`texture_hash` が常に `0` です。writer のカットアウト（§2-5）に使うテクスチャは、同じ rank の自分の色の DrawBatch か、パーツのセルから取ってください。マスクの DrawBatch の `texture_hash` で引くと、テクスチャが見つかりません。

> [!IMPORTANT]
> **クリッピング（`mask_write`）にはマスクの DrawBatch が出ません。** クリッピングは通常の描画の DrawBatch としてだけ出るので、`Mask` の DrawBatch だけを見る Player は **クリッピングをすべて取りこぼします。** writer は、PartData を読んで Player が決めてください（§1-3 の 3 つの式）。

**非表示の writer**: Brain は `Hide == true` のパーツを `draw_order` と DrawBatch から除きます。writer ではマスクパーツとクリッピング（`mask_write` の描画パーツ）がこれにあたります。例外は `draw_as_mask` でマスクにした描画パーツで、**`Hide == true` でもマスクの DrawBatch が出ます**（止まるのは自分の色の描画だけで、形は書かれます）。writer が働くかは、**`mask != 0` と `Hide == false` の両方**を Player で判定してください（§2-2）。Brain が除いたパーツを重ねて除くだけなので、この判定はどちらの場合も安全です。

**`mask_indices` を writer の一覧として使わないでください。** FrameData の `mask_indices` は純粋なマスクのパーツの列ですが、**クリッピングを含まず**、**`Hide == true` のマスクパーツも除いていない**ので、`draw_order` と一致しません。writer は、`draw_order` を走査して §1-3 の式で決めてください。

**`DrawBatch.flags` のビット `0x01`** は、その DrawBatch のパーツが `mask_influence == 1` であることを表します。

## 4. ステンシルでの実装

SpriteStudio のマスクは、ステンシルバッファに沿った設計です。エンジンがステンシルを使わせてくれる場合は、それを使うのが素直です。

1. `draw_order` を順に走査する
2. writer が来たら、カットアウトの閾値で `discard` した残りの画素について、書き込み方（加算 / 反転）でステンシルを更新する
3. 対象が来たら、ステンシルの値と `visible_inside_mask` で描くかを判定する

> Unity の Shader Graph のようなノードで組むシェーダは、ふつうステンシルの細かな指定ができません。マスクの処理だけは、手書きのシェーダ（HLSL など）や専用の RenderPass に分ける必要があることがあります。

### 4-1. writer と対象のステンシルの設定

マスクは 2 種類の描画に分かれます。**writer**（マスクの形をステンシルに書く）と、**対象の判定**（書かれたステンシルを読んで内外を判定する）です。

- **writer**: 色は書きません（`ColorMask 0`）。ステンシルは常に更新し（`Comp = Always`）、更新の演算 `Pass` を書き込み方（§2-3）で切り替えます。
    - 加算 → `IncrementWrap` / `DecrementWrap`（**カウンタ**。重なった枚数を数える）
    - 反転（`mask_influence == 1`）→ `Invert`（奇数か偶数か。自分自身が逆の演算になる）
    - **この 2 つに同じビットを使わせないでください。** 2 つは交換できないので、混ぜると結果が描く順番に依存し、打ち消しても 0 に戻りません（§4-4）。`WriteMask` を書き込み方ごとに分けます。
    - `Ref` は使いません（置き換えではないので `0` でよい）。カットアウトは §2-5 の閾値でフラグメントを `discard` します（シェイプのように形そのものがマスクなら、閾値を負にして `discard` しない）。
- **対象の判定**: ふつうの色の描画に、**ステンシルのテストだけ**を加えます。極性（§2-4）は `Comp` で表します。
    - `visible_inside_mask`（内側に描く）→ `NotEqual`（マスクのビットが立っている画素で通す）
    - 外側に描く → `Equal`
    - `Ref = 0` とし、テストではステンシルを**書きません**（`WriteMask = 0`）。

つまり、**極性（内か外か）は writer ではなく対象の側**が持ちます。

### 4-2. ステンシルを元に戻す

描く前にステンシルを退避して後で戻したくなりますが、SpriteStudio のマスクは**演算の対称性で自分を打ち消す**設計なので、退避と復元も、クリアの描画も要りません。

- **純粋なマスク**: すべてのパーツより前に形を加算しておき、**自分の `draw_order` の rank で同じ形を減算**します。これでフレームの中での差し引きが **0** に戻り、「マスクは自分より描画優先度の低い（前の）パーツにだけ効く」というスコープ（§2-1）も自然に出ます。反転なら `Invert` を 2 回で同じように打ち消せます。
- **クリッピング**: 自分の rank で書き、**そのアニメーションの描画がすべて終わった後**に同じ形を逆の演算で打ち消します。切り取る相手（自分より後のパーツ）をすべて描いてから戻すので、**アニメーションの中の見え方は変わらず**、差し引きはアニメーションの描画の後に **0** に戻ります。反転なら `Invert` を 2 回。
    - **この打ち消しは省けません。** ステンシルがクリアされるのは、カメラやフレームの始めの **1 回だけ**です。同じフレームで SpriteStudio のアニメーションを複数描くと、**アニメーションの間ではクリアされない**ので、クリッピングのビットを残すと、後に描くアニメーションのマスクの判定を汚します（§4-3 のビットの隔離は URP などの他の用途からは守りますが、**同じビットを使う別の SpriteStudio のアニメーションからは守りません**）。

要点は、**「クリアや退避と復元ではなく、増減の対称性で、アニメーションの描画の中に状態を閉じ込める」** ことです（純粋なマスクは自分の rank で、クリッピングはアニメーションの描画の最後で打ち消す）。コストは打ち消しのために形をもう一度作ることだけで、マスクの数は少ないので小さく済みます。

**インスタンスの中のクリッピングの持ち越し**（§2-7）をステンシルで実装するには、上のクリッピングの「アニメーションの描画の最後で打ち消す」を、**インスタンスの境界を越えて、親アニメーションの描画の最後まで遅らせます。**

- 子アニメーションはふつうに描画を組み立てますが、**クリッピングを閉じる（逆の演算の）描画に「遅らせてよい」印**を付けておきます（描画の役割は書き込みのまま）。
- 親が子をインスタンスとして取り込むとき、**その閉じる描画をインスタンスの境界では出さず**、親のインデックスに書き換えて取っておき、**親自身の描画の最後にまとめて出します。** これで、子の中のクリッピングが、インスタンスより後に描かれる親のパーツも切り取ります。出すときにも印を残せば、**入れ子は上の親へ順に送られます。**
- **この処理は、親が自分でマスクを持つかどうかにかかわらず行います。** 「親には writer が無く、子にだけある」構成でも子の持ち越しを流す必要があるので、親のマスクの有無でこの処理を止めないでください。表示中のインスタンスが開いたクリッピングを残していたら、**インスタンスより後の親のパーツを対象**として判定します（§2-7）。
    - 「インスタンスより後のパーツ」には、**後に描かれるインスタンスの子アニメーション**と**エフェクトのパーティクル**も含まれます。子を取り込む直前にその子を組み立てる Player では、組み立てる時点では、どの前のインスタンスがクリッピングを開いたまま残すかがまだわかりません。そこで、階層が自分のマスクを持つか、下のどこかにクリッピングがあるときは、組み立てる前のすべての子に「外からの被覆が有効かもしれない」と伝えてください。伝えないと、自分では writer を持たない後の子が、判定されずに描かれます。
- **遅らせた閉じる描画が抜けた隙間をまたいで、描画を結合しないでください。** 閉じる描画を取り出すと、子の最後の描画と親の次の描画は、インデックスバッファの上で隣り合わなくなります。同じマテリアルの隣り合う描画を 1 つのインデックスの範囲にまとめる Player では、範囲が連続していることを確かめてください。前の範囲を後ろの範囲まで伸ばすと、間にある閉じる描画のインデックスも含んでしまい、その形を色付きで描きます。
- 持ち越した writer の書き込み方とプレーンは、**実効 `mask_influence`**（§2-7）で決めます。閉じるのは対応する書き込みの逆の演算（`Invert` はそれ自身、加算 ↔ 減算）を同じプレーンに行うだけなので、§4-4 のプレーンの分離はそのまま保たれます。

### 4-3. エンジンがステンシルを常に使う場合（URP など）

URP をはじめ多くの描画パイプラインは、**ステンシルを自分の用途で常に使っています**（ライト、Decal、Rendering Layers、SSAO、deferred のマテリアルの種類、カメラのスタックなど）。その上に SpriteStudio のマスクをそのまま重ねると、互いに壊し合います。

**`ReadMask` / `WriteMask` で、SpriteStudio のマスク専用のビットの範囲に閉じ込めてください。** SSPlayerForUnity では **下位 4 ビット（`0x0F`）** に限っています。

- これは URP のステンシルの割り当て（bit 0–3 = UserMask / bit 4 = light / bit 5–6 = material type / bit 7 = reserved）の**空いているビット**に当たるので、URP の機能と共存できます（Built-in パイプラインも同じ割り当て）。
- `WriteMask` は `0x0F` の**内側**です（さらに書き込み方ごとに分けます。§4-4）。`IncrementWrap` の桁上がりが bit 4（URP の light）に**漏れません**（マスクで落とされます）。
- `ReadMask = 0x0F`: テストは**自分のビットだけ**を見るので、URP が bit 4–7 に書いた値を無視できます。
- 4 ビットを書き込み方ごとに分ける（§4-4）ので、**カウンタに使えるのは 3 ビット = 重ねて 7 枚まで**です。反転の側は奇数か偶数かだけなので、枚数の上限はありません。ビットを **`0x0F` より広げると、URP の予約ビットを壊し、壊されます。**

移植先のパイプラインがステンシルを使う場合は、同じように**専用のビットの範囲を選び、Read / Write のマスクで囲ってください。** ビットを確保できない、あるいはステンシルそのものを使えないエンジンでは、§5 の被覆ビットマップ（ステンシルを使わない）に切り替えます。

### 4-4. 書き込み方ごとにビットのプレーンを分ける（必須）

`Invert` と `IncrementWrap` / `DecrementWrap` は、**それぞれ単独では自分の逆の演算を持ちますが、互いには交換できません。** 同じビットを使うと、`mask_influence` の違う writer が重なった部分で、次の 2 つが起きます。

- **結果が描く順番に依存する**: `加算 → 反転` は `0 → 1 → 254`（書かれている）、`反転 → 加算` は `0 → 255 → 0`（**書かれていない**）。同じ 2 枚でも、描いた順で結果が逆になります。
- **打ち消しても 0 に戻らない**: `加算（1）→ 別の反転（254）→ 減算（253）`。残った値は、後に描くすべてのパーツのマスクの判定を汚し、§4-2 の打ち消しが成り立たなくなります。

ステンシルへの書き込みは `新しい値 = (演算(古い値) & WriteMask) | (古い値 & ~WriteMask)` です。演算は値全体に対して行われますが、**書くビットを限れば桁上がりと桁借りが捨てられ、各プレーンが閉じます。** そこで、書き込み方ごとに `WriteMask` を分けます。

| 書き込み方 | プレーン | 必要なビット | 重ねられる数 |
|---|---|---|---|
| `Invert` | **パリティ** | 1 ビット | 奇数か偶数か。**上限なし** |
| `IncrementWrap` / `DecrementWrap` | **カウンタ** | 残りの `n` ビット | 和集合。`2^n - 1` 枚まで |

- パリティは 1 ビットで足ります（`Invert` はそのビットを反転するだけで、カウンタに触れません）。
- カウンタは **bit 0 から連続**している必要があります（増減はふつうの算術なので）。
- **対象の判定は変えなくてかまいません。** `ReadMask` は両方のプレーンを含む全体のまま、判定も「値 ≠ 0」のままで、これが **2 つのプレーンの和集合** になります。`mask_influence` の違うマスクが重なったときは和集合になる、という仕様と一致します。

SSPlayerForUnity では、§4-3 の `0x0F` を **パリティ `0x08` / カウンタ `0x07`** に分けています（`mask_influence == 0` のマスクは 7 枚まで重ねられる）。

**この規則は実装方式によりません。** §5 の被覆ビットマップも同じ演算を再生して再現するので、そのまま当てはまります。ただし分けるのは「ビット」ではなく**積算する変数**で、ビットの予算を分ける必要がないので、上の枚数の上限もありません（§5-1）。

## 5. ステンシルの無いエンジンでの実装（被覆ビットマップ）

たとえば Godot の 2D の canvas は、ステンシルバッファを使わせてくれません（4.7 の時点で、ステンシルを持つのは 3D のマテリアルだけです）。そうしたエンジンでは、次の方法でステンシルを再現できます。

1. **被覆ビットマップを作る**: フレームごとに、そのときのすべての writer を画面外の被覆ビットマップに描きます。writer ごとに 1 ビットを割り当て、形が覆う画素にそのビットを立てます。
2. **描くときに再生する**: 対象のシェーダで被覆ビットマップを読み、その対象に効く writer を再生してステンシルの状態を組み立て、`discard` で内外を切り取ります。

要点は、**「描く時刻に依存する状態を持たず、被覆（writer の形）と再生（対象の側での組み立て）に分ける」** ことです。RGBA8 の RGB の 3 チャンネルに 8 bit × 3 = 24 bit を使えば、1 枚の被覆で **writer 24 個**まで扱えます。

インスタンスを使うと writer が増えます。インスタンスの writer は、そのインスタンスを置いた回数だけ数え直しになり、1 枚の被覆をインスタンスの階層全体で使う（§5-2）ので、24 個はすぐに足りなくなります。テクスチャを大きくするのではなく、**同じテクスチャをタイルに分けてください。** 横に 2 つ、次に 2x2 に分け、どのタイルにも同じ外接矩形を写して、タイルごとに 24 ビットを持たせます。再生では、必要なタイルの同じ位置の画素を読みます。メモリを増やさず、解像度と引き換えに writer を増やせます。SSPlayerForGodot は 4 タイル（writer 96 個）までにして、それを超えた分は警告を出して無視しています。

**被覆ビットマップの大きさ**は、writer 全体の外接矩形に合わせて変え、**長辺を上限（例: 1024 px）に揃える**のが実用的です。フル HD 程度の画面で画素と同じ精度を保ちつつ、1 枚あたり最大 4 MiB（RGBA8）に収まります。アニメーションをたくさん同時に表示する場合は、画面の解像度に合わせたり、小さなプールで共有したりして、さらに減らせます。

**外接矩形の外**にある対象のパーツは、writer が無いのと同じ扱い（マスクされない）にしてください。テクスチャの端の CLAMP による誤ったマスクを避けられます。

### 5-1. 擬似コード

インスタンスを持たない 1 つのアニメーションについて、エンジンによらない擬似コードで全体の流れを示します。インスタンスへの広げ方は §5-2 です。

各 writer は、**描画の順番の開区間**の間だけビットを持ちます（§2-1）。純粋なマスクはアニメーションの先頭から自分まで、クリッピングは自分から最後までです。対象には、自分の位置を含む区間を持つ writer が効きます。

**データの構造（最大 24 writer、RGBA8 の RGB に 8 bit × 3）**

```
const int   MAX_WRITERS = 24;
const float SEQ_END     = 16777216.0;  // どの位置よりも後。float でも正確に表せる

struct MaskWriter {
    int   part_index;    // パーツのインデックス
    int   bit;           // 0..23、被覆の中のビットの位置
    float open;          // open < p < close の位置 p でビットを持つ
    float close;
    bool  op_invert;     // 書き込み方: false = 加算, true = 反転
};
```

**writer を決める（毎フレーム）**

```
function build_mask_writers(frame) -> [MaskWriter]:
    writers = []
    for rank, part_index in enumerate(frame.draw_order):
        part = frame.parts[part_index]
        // part.data.* = PartData（静的）/ part.frame.* = FrameData（毎フレーム）
        pure_mask  = part.data.type == Mask || part.data.draw_as_mask
        is_writer  = pure_mask || part.data.mask_write
        if not is_writer:               continue
        if part.frame.mask == 0:        continue       // §2-2
        if part.frame.hide:             continue       // §2-2 / §3
        if len(writers) >= MAX_WRITERS: break

        is_clipping = part.data.mask_write && !pure_mask
        writers.append(MaskWriter {
            part_index  = part_index,
            bit         = len(writers),                 // 0, 1, 2, ...
            // §2-1 スコープ: クリッピング = 自分より後 / マスク = 自分より前
            open        = is_clipping ? rank    : -1,
            close       = is_clipping ? SEQ_END : rank,
            op_invert   = part.data.mask_influence,     // §2-3（純粋なマスクとクリッピングで共通）
        })
    return writers
```

**被覆ビットマップを描く（毎フレーム）**

画面外の RGBA8 のビューポートに、加算の合成で各 writer の形を描きます。ビットが重ならないので、加算がビットの OR になります。各 writer は、自分のビットだけが立つ色で描きます。

```
function render_coverage_bitmap(writers, frame) -> Bitmap:
    bitmap = create_offscreen_RGBA8_with_additive_blend()
    for w in writers:
        channel   = w.bit / 8                          // 0 = R, 1 = G, 2 = B
        bit_val   = (1 << (w.bit % 8)) / 255.0
        bit_color = vec4_zero_except(channel, bit_val)
        threshold = (255 - frame.parts[w.part_index].frame.mask) / 255.0

        draw_geometry(
            geometry = geometry_of(w.part_index),       // 通常 = スプライト / メッシュ / シェイプ
            shader   = MASK_WRITE_SHADER,
            uniforms = { mask_bit_color: bit_color, mask_threshold: threshold }
        )
    return bitmap
```

**ビットを書くシェーダ（GLSL）**

```glsl
uniform vec4  mask_bit_color;   // 該当する RGB チャンネルに入れたビット
uniform float mask_threshold;   // (255 - mask) / 255

void fragment() {
    // §2-5 カットアウト: アルファが閾値を超える画素だけを書く
    if (texture(TEXTURE, UV).a <= mask_threshold) discard;
    // 加算の合成は src.rgb * src.a で動くので、アルファは 1 にする
    COLOR = vec4(mask_bit_color.rgb, 1.0);
}
```

**描くときの再生（対象のシェーダ、GLSL）**

```glsl
uniform sampler2D coverage;
uniform int   mask_count;
uniform vec4  mask_meta[MAX_WRITERS]; // (open, close, bit, op_invert)。MaskWriter と対応
uniform float this_rank;              // 対象の、描画の順番の中の位置
uniform float visible_inside;         // §2-4 極性（1 = 内側 / 0 = 外側）

bool mask_passes(vec2 cov_uv) {
    // writer が 1 つも無い: どこもマスクされていないので、極性だけで決まる
    if (mask_count == 0) return visible_inside <= 0.5;
    // 外接矩形の外は writer が無いのと同じ（端の CLAMP による誤ったマスクを避ける）
    if (cov_uv.x < 0.0 || cov_uv.x > 1.0 || cov_uv.y < 0.0 || cov_uv.y > 1.0)
        return visible_inside <= 0.5;

    vec4 cov = texture(coverage, cov_uv);   // サンプラーは nearest にする
    // §4-4 のプレーンの分離。ここは本物のステンシルではなく変数なので、
    // ビットの予算を分けず、積算する変数を 2 つに分けるだけでよい。
    int parity = 0;   // 反転（mask_influence == 1）: 奇数枚の重なりで書かれている
    int count  = 0;   // 加算（mask_influence == 0）: 1 枚でもあれば書かれている
    for (int i = 0; i < mask_count; i++) {
        vec4 m = mask_meta[i];
        // §2-1 スコープ: writer は開区間 (open, close) の間だけビットを持つ
        bool active = this_rank > m.x && this_rank < m.y;
        if (!active) continue;
        // 被覆から、この writer のビットを取り出す
        int bit  = int(m.z + 0.5);
        int byte = int(cov[bit / 8] * 255.0 + 0.5);
        if (((byte >> (bit % 8)) & 1) == 0) continue;
        // §2-3 書き込み方（§4-4: この 2 つを同じ変数に混ぜない）
        if (m.w > 0.5) parity ^= 1;                     // 反転
        else           count  += 1;                     // 加算
    }
    bool masked = (parity != 0) || (count != 0);        // 2 つのプレーンの和集合
    return masked == (visible_inside > 0.5);            // §2-4
}

void fragment() {
    // ... ふつうの色の計算 ...
    if (!mask_passes(coverage_uv)) discard;
    COLOR = ...;
}
```

- **被覆のサンプラーは nearest にしてください。** linear では隣のビットが混ざって、正しく読めません。
- **外接矩形の外と、writer が 1 つも無いときは、`visible_inside` だけで決めます**（そこはマスクされていない）。内側に描く対象は、マスクを持たないアニメーションでも判定してください。省くと、SpriteStudio では隠れるところに描かれます（§2-4）。
- 対象の `this_rank` と、各 writer の区間 `mask_meta[i].xy` を比べます（§2-1）。
- **反転と加算を同じ変数に混ぜないでください**（§4-4）。1 つの変数に両方を適用すると、`mask_influence` の違う writer が重なった部分で、結果が **writer の並び順に依存** します（`加算 → 反転` は書かれている、`反転 → 加算` は書かれていない）。
- ただし **再生の側にビットの予算はありません。** 本物のステンシルではなくシェーダの変数なので、§4-3 の「カウンタ 3 ビット = 7 枚」のような上限は無く、writer の数（24）まで重ねられます。

### 5-2. 被覆の UV と、インスタンスへの引き継ぎ

**被覆の UV**: 再生のシェーダの `coverage_uv` は、頂点シェーダで、**対象の Player のローカル座標を被覆の UV `[0, 1]` に写すアフィン変換** `M`（外接矩形で正規化する 2x2 の基底とオフセット）で求めます。被覆ビットマップは writer を持つアニメーションの外接矩形に張るので、`M` はそのアニメーションの Player のローカル座標が基準です。

**インスタンス**: 呼び出す側のマスクはインスタンスの子アニメーションに及び、子アニメーションの中で書かれたマスクは子自身のパーツに効き、そのクリッピングは呼び出す側へ持ち越されます（§2-6 / §2-7）。入れ子の深さは問いません。被覆ビットマップでは、これらはすべて **インスタンスの階層全体の描画の順番に番号を振る** ことに帰着します。被覆ビットマップは **最上位のアニメーションが 1 枚だけ** 持ちます。

1. **階層全体に番号を振る。** 最上位のアニメーションの `draw_order` を順にたどり、各パーツに次の番号を振ります。そのパーツが表示中のインスタンスパーツなら、その番号を振ったあと、子アニメーションの `draw_order` に同じように（再帰的に）番号を振ってから先へ進みます。子アニメーションはインスタンスパーツの位置に描かれるので、この順番が描画全体の順番になります。この番号を `seq` と呼びます。
2. **階層のすべての writer を 1 枚の被覆に描く。** 子アニメーションの writer の形は、インスタンスの配置行列の連鎖（`slot_xf`、子のローカル座標 → 親のローカル座標）で最上位のアニメーションのローカル座標に写し、外接矩形にも含めます。各 writer は `seq` の開区間の間だけビットを持ちます（§2-1）。
    - **純粋なマスク**: **自分のアニメーションの先頭**（インスタンスパーツの `seq`。最上位なら `-1`）から **自分まで**。自分のアニメーションの外には及びません。
    - **クリッピング**: **自分から階層全体の最後まで**（`SEQ_END`）。インスタンスの中のクリッピングは、呼び出す側でその後に描かれるパーツも切り取り続けます（§2-7）。深さは問いません。
    - 書き込み方: writer の実効 `mask_influence`（§2-7）。
3. **`seq` で再生する。** `mask_meta` は §5-1 と同じ `(open, close, bit, op_invert)` で、対象は自分の `seq` を `this_rank` として渡します。§5-1 のシェーダはそのまま使えます。
4. **子のパーツの UV と設定。** UV の変換を階層に沿って合成します（`M_child = M_parent · slot_xf`）。これで子の各頂点が最上位の被覆に写ります。子の各パーツは、受けるかどうかと極性を §2-6 の合成（インスタンスパーツの値だけ）で決めます。

- **持ち越しのための別の処理は要りません。** 各 writer がどこまで効くかは区間が表しています。純粋なマスクは自分のアニメーションの中で閉じ、クリッピングは階層の最後まで効きます。ステンシルでは閉じる処理を遅らせて打ち消します（§4-2）が、被覆ビットマップには戻す処理がありません（再生が対象の側で状態を組み立てるため）。
- **最上位のアニメーションが自分の writer を持たなくても**、階層のどこかのアニメーションが持っていれば、この処理を行います。
- **階層全体の writer がビットの予算を分け合います。** インスタンスの writer は、置いた回数だけ数え直しになります。24 個で足りなければタイル（§5）を使ってください。
- 子アニメーションのパーツは、最上位のアニメーションが番号を振るより前に決まるので、子はまだ、どの writer が自分のどのパーツに効くかを知りません。子では、マスクを受けるパーツをすべて判定の対象にしてください。すべての区間を知っている最上位のアニメーションは、どの writer にも覆われないパーツの判定を省けます（内側に描くパーツは除く）。

### 5-3. 被覆ビットマップの大きさの段階と、1 フレームの遅れ

被覆ビットマップを外接矩形に合わせて大きさを変え（§5）、画面外の描画先を**プールで使い回す**場合に、連続して拡大・縮小するマスクで起きる問題と対策です。基本の方式はこの節が無くても動きますが、マスクを激しく連続でズームさせると、1 フレームだけマスクが抜けて見えることがあります。

**大きさの段階（2 の冪に揃える）**

外接矩形の画素の大きさをそのまま描画先の大きさにすると、毎フレーム描画先を作り直すことになり、無駄です。各軸の大きさを **2 の冪の段階に切り上げ**（… / 256 / 512 / 1024）、その段階の描画先をプールから借ります。段階 `C` は `C/2 < px ≤ C` を受け持つので、境界を越えたときだけ別の段階に切り替わり、滑らかに拡縮する通常の場合は描画先を使い回せます。

読む側の UV は §5-2 の `M`（外接矩形での正規化）なので、**大きさの段階によりません**（同じ Player のローカル座標の外接矩形を、常に `[0, 1]` に写す）。どの段階の被覆を貼っても、対象は正しく切り取られます。

**1 フレームの遅れと、段階が変わるフレームの抜け**

多くのエンジンでは、画面外の描画先は **1 フレーム遅れて**しか読めません（そのフレームに描いた被覆は次のフレームで読める。例: Godot の Viewport のテクスチャ）。ふつうはマスクが 1 フレーム遅れるだけで、問題になりません。

問題は、大きさの段階が変わる **フレーム** です。新しい大きさの描画先を借りると、そこには **まだ有効な被覆がありません**（まだ描いていないか、別の用途の残り）。1 フレーム遅れるので、そのフレームには読めず、そのままでは **そのフレームだけマスクが効かず**、切り取るはずのパーツが切り取られずに描かれます。連続でズームすると、境界を越えるたびにちらつきます。

**対策 1: 段階が変わるフレームは古い描画先を読む**

段階が変わるとき、古い描画先をすぐに返さず **1 フレームだけ持っておき**、そのフレームは **古い描画先の（前のフレームに描いた）被覆を読みます。** UV は段階によらないので、古い描画先（前の解像度）でも対象は正しく写り、これは **ふつうのフレームと同じ 1 フレームの遅れ**（その 1 フレームだけ前の解像度）でしかありません。マスクは抜けません。新しい描画先にはそのフレームの被覆を描いておき、次のフレームからそちらに切り替えます。

**対策 2: 縮小の側にだけ余裕を持たせる**

外接矩形の大きさが段階の境界のあたりで揺れると、段階が毎フレーム入れ替わり（512 ↔ 1024 …）、切り替えが頻発します。これを防ぐため、**縮小の判定にだけ余裕を持たせます。** 拡大はすぐに行い（解像度を落とさない）、縮小は境界を **十分に下回るまで今の段階を保ちます。** 拡大を遅らせると被覆の解像度が足りず縁が荒れる（見える劣化）一方、縮小を遅らせても VRAM が少し増えるだけ（見えないコスト）だからです。

余裕の幅に唯一の正解はありません。SSPlayerForGodot は `0.15`（境界を 15% 下回るまで今の段階を保つ）を使っています。切り替えをさらに減らしたければ上げ、小さなマスクが大きな描画先に長く居座る VRAM が気になれば下げてください。

対策 1 は「切り替わっても抜けない」、対策 2 は「無駄な切り替えを減らす」を受け持ち、互いに補います。

**止まっているフレーム**

次のフレームの大きさの段階を、そのフレームの外接矩形から決める場合、進んでいないアニメーション（一時停止中、停止中、エディタでの表示）は次のフレームを描かないので、最初の段階で描いた被覆のままになります。最初の段階が小さいと、タイル（§5）で分けていればなおさら、マスクが粗く出ます。選んだ段階が、いま描くのに使った段階と違うときは、止まっているフレームをもう一度だけ描いてください。
