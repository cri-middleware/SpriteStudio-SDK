# Player 実装方針の検討

# 利用する libssruntime のバイナリタイプと取得方法
利用する libssruntime のライブラリタイプとライブラリファイルの取得方法を決めてください。
1 つのゲームエンジンで対象プラットフォーム毎にライブラリタイプが異なるケースもあります。どのライブラリタイプを利用するか、そのライブラリをどう取得するかを決めてください。

# ライブラリタイプ
- 静的ライブラリ
    - C/C++ では成果物に取り組むことが多いのでこちらのケースが多いです。
- 動的ライブラリ
    - C/C++ 以外のネイティブライブラリをバインディングする言語では動的ライブラリを利用するケースが多いです。

# 取得方法
- SpriteStudio7-SDK がリリースしているバイナリをダウンロードして利用する。
- 自前でビルドを実施する。
    - libssruntime をカスタマイズする場合はこちらを選択してください。


# さらに
ユーザビリティ向上のため Player 以外の実装も必要かを確認をお願いします。
- sspj プロジェクトから ssab ファイルをコンバートする拡張機能をゲームエンジンの開発エディタに追加するかを検討してください。
    - Windows, macOS, Linux 向けの libssconverter の用意も必要になります。

# 内部構造の検討
Player の実装は「ゲームエンジンのオブジェクトのパーツの階層をもつ作り」にするかあるは「テクスチャにレンダリングをする」二つの方法があります。
それぞれの実装のメリットとデメリットは下記になります。

## GameObject 的に分割した場合
- メリット
    - 各パーツに連動したりするエンジンのオブジェクトをぶら下げたりしやすい
    - 座標系がゲームエンジン側と統一できるので、結構楽に扱える。
- デメリット
    - なんだかんだで、エンジン側のゲームオブジェクトの処理に足を引っ張られる場合がある（主に使用制限や動作速度面において）。あとパーツ毎でレンダリングを仕掛けたりする場合、オーバーヘッドが生じる場合が多い。
    - パーツ毎でプライオリティ（実際の描画のZ深度）が変わる場合があるので、Zファイト（パーツがZ深度でチラついたり・他の3Dオブジェクトを挟み込んじゃったりする）が起きやすい
    - 2Dパーツ全体にエフェクトとかかけたい場合に若干面倒になる場合がある。

## テクスチャにレンダリングした場合
- メリット
    - 1枚になるので、端的に扱えはする。
    - オフスクリーンレンダリングとの相性は良い
- デメリット
    - VRAMを余分に食っちゃったり・テクスチャの大きさの関係でアニメーションがかけちゃったりする場合がある
    - 合成結果が異なる場合がある（一度レンダリングしちゃってるので、加算とか減算とかそのあたりの計算結果が異なっちゃう場合が多々生じます。穏便に済むのは「通常」と……あとは工夫すると「加算」もいけはするのですが、他の合成方法は大半上手くいきません）

# 対応する ssab ファイルのタイプの検討

ssab は下記の種類のファイルタイプがあります。

- Reference
    - アセットファイルを参照する。
- Embedded
    - アセットファイルをデータとして ssab に埋め込む

実装する Player は Reference と Embedded のサポートをするかを判断してください。
ゲームエンジン向けの Player であれば Reference, ウェブやアプリ向けの Player であれば Embedded がおすすめです。

- Reference のみを実装し、Embedded に対応しない場合
    - 追加の作業はありません。
    - ドキュメントへ Embedded をサポートしないと明記してください。
- Reference に対応ぜず、Embedded の ssab のみに対応する場合
    - アセットのロード部分を ssab データからアセットを取得する実装にしてください。
    - Embedded のみをサポートすると明記してください。
- Reference, Embedded 両方の ssab に対応する場合
- ssab データにアセットが組み込まれているかを判断して、存在したら Embedded で動く、なかったら Reference で動くように実装してください。
