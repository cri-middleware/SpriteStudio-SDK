# オーディオ（サウンド）再生の統合

オーディオパーツから発行される `audios` イベントは、ランタイム内では音声再生を行わず、各プラットフォームのプレイヤー側でエンジンごとのオーディオAPIを用いて再生する必要があります。
完全なオーディオ対応を行うには、単なる再生トリガーだけでなく、再生状態（ライフサイクル）の管理が必要です。

- **事前ロード (Preload) の必要性**:
  - オーディオファイルのダウンロードやデコードには時間がかかります。イベント発火時にロードを開始すると音声が遅延するため、アニメーションの設定（セットアップ）時などに、SSAB内に定義された音声を抽出し、オーディオエンジン側で事前にメモリにデコード（事前ロード）しておくことを強く推奨します。
- **遅延初期化 (Lazy Initialization)**:
  - 音声を使用しないプロジェクトで無駄にオーディオエンジン（Web Audio API の `AudioContext` など）が起動してリソースを消費するのを防ぐため、SSAB内に音声データが含まれていることを検知した初回のみオーディオエンジンを生成する（遅延初期化）設計が望ましいです。
- **基本的な再生**:
  - オーディオは毎フレームの更新時に発火する `audios` イベントを契機として再生されます（`ss_runtime_get_passed_event_count` / `index` を使用して取得します）。
  - **重要**: イベント処理は逆再生時にも発火しますが、逆方向の音声再生はオーディオAPI側でサポートされていないことが多いため、**順再生（再生速度 > 0 かつ 前進方向）の時のみ音声を再生**するようにフィルタリングを行う必要があります（逆再生時の音声再生は制限事項となります）。
  - SpriteStudioエディタ本体とは異なり、Playerの実装では**シーク（任意のフレームへのジャンプ操作）によるオーディオの再生位置（オフセット）の同期は行いません**。音声はあくまでタイムライン上の該当フレームを**通過した瞬間（イベント発火時）のみ再生**される仕様となります。
  - `loopNum` はその名の通り「ループ回数」という変数名ですが、実質的には「再生回数」を表します。1以上の値が指定され、その回数分だけ再生を繰り返します。SpriteStudioのオーディオには無限ループの概念はありません。
- **音は、それを発火させた再生よりも長く生き残ります**:
  - **再生制御は音の寿命を持ちません。** `pause` / `resume` / `stop` / `setup_animation` が終わらせる（あるいは保持する）のは *アニメーション* であって、すでに鳴っている音には触れません。これは実装の手抜きではなく、Player が守れる唯一の定義です。voice を一時停止しても届くのは「すでに鳴っている音」だけで、その保持中に通過するはずだったキーの音は鳴らず、`resume` でも取り戻せません。保持のつもりが穴になります。また `loopNum` は再生回数であり無限指定が存在しないため、すべての音はいつか自然に終わります。停止やアニメーション切り替えで音を一掃する Player は、暴走を防いでいるのではなく、鳴り切るはずの音を途中で切っています。アニメーションの尺より長く鳴る音があるなら、それはアニメーションデータ側の問題です。
  - **例外は破棄時のみ**です。Player 自身が消えるとき（破棄、無効化、シーンからの除去）は、自分が鳴らした音をすべて停止しなければなりません。その voice を持つものが誰もいなくなるためです。あわせて「今すぐ音を止める」明示的な API をホストに提供してください。要点は、Player が勝手にその判断をしない、ということです。
  - 公式 Player はすべてこの方針です。Godot は `NOTIFICATION_EXIT_TREE` と破棄時、Unity は `OnDisable` / `OnDestroy`、Web は `destroy()`、Ren'Py は `hide` / `scene` で停止します。それ以外で音が止まることはありません。
- **起点フレームのイベント発火（実装上の注意）**:
  - `play()`（およびフレーム指定つきの再生開始）の直後、最初の `update` は起点フレーム（例: フレーム0）を「通過したフレーム」として報告します。これはランタイム内部の再評価フラグ（`needs_evaluation`）により、`ss_runtime_get_passed_event_count` / `index` に起点フレームが含まれる挙動です。フレーム0に配置された音（`LoopNum` 付きのオーディオキー等）はこの仕組みによって初回再生から発火します。
  - このため、**イベントの取得・処理を「描画フレームが前回と変わったか」といった描画側の最適化条件でゲートしてはいけません**。起点フレームで整数フレームが進まない tick（初回の経過時間が短い場合など）に early-return してしまうと、ランタイムが報告済みの起点フレームイベントを取りこぼします。この取りこぼしは初回 tick の経過時間に依存するため、実行環境によって「鳴る/鳴らない」が分かれる再現しにくい不具合になります（例: プロジェクト実行では鳴るがエディタプレビューでは鳴らない、等）。イベントは描画の有無に関わらず、ランタイムが報告した時点で必ず処理してください。
- **シーク（フレームジャンプ）との関係（制限事項）**:
  - 上記の再評価フラグはフレームのシーク（`ss_runtime_set_frame_no` 等）でも立つため、**再生中に任意フレームへシークすると、次の `update` でそのフレームのイベント（オーディオを含む）が発火します**。「シークではオーディオの再生位置同期・再生を行わない」を厳密に守りたい場合は、再生開始（`play`）以外を契機に立った再評価フラグ相当のフレームについて、プレイヤー側でオーディオ発火を抑制する実装が必要です。
  - なお、停止中のスクラブ（再生していない状態でのフレーム移動）は `update` が回らないため音は鳴りません。考慮が必要になるのは「再生中のシーク」に限られます。
