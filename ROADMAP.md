# SpriteStudio-SDK — Roadmap

Each item below states a **primary deliverable**. A few entries also list **Co-decided** sub-bullets — those are design points settled as part of the parent work so adjacent API contracts stay consistent. They are not separate tasks and should not be split into independent issues. This file lists unfinished work and deliberate non-goals only; concrete API and design belong with the code and the Player Porting Guide.

## Phase 3: Feature Expansion (Post-Release)

*(Phase 3 is post-release work, implemented without `.fbs` schema changes — additions go to FFI APIs and runtime state only; any item that turns out to need a schema change is reconsidered for an earlier phase.)*

- [ ] **Discrete-attribute resolution through the mix** — the topmost covering track above a threshold wins (modelled on Spine's `mixAttachmentThreshold`). Specified but unbuilt: discrete attributes (visibility, cell) come from track 0 today, because cell switching goes through the Override Layer. It must re-evaluate `DrawBatch` split points after the mix.
- [ ] **Per-source playback control** — `play` / `pause` / `loop` / `is_finished` act on track 0 only, while secondary sources have frame, speed and weight; VTuber-style overlay tracks want their own loop control.
- [ ] **Crossfade interruption** — interrupting a running crossfade settles it first (the incoming animation takes the track at full weight, the outgoing source is released) and the new fade starts from there, so the pose can jump. Spine keeps a `mixingFrom` chain instead; define a cleanup rule for abandoned sources before considering one.
- [ ] **Event-threshold default** — `1.0` here against Spine's `0`; revisit now that "primary" has weakened into "track 0".
- [ ] **Per-part size override** — extend the Override Layer with `size_x` / `size_y`. This is what the Player family's UI work is blocked on: a Nines part's size comes from its keyframes, so an authored window frame cannot follow the box its host's layout gives it, and scaling the player distorts the border art instead of stretching the middle. Six of the seven Player roadmaps carry the item and name this as the dependency — ForUnity, ForGodot, ForFlutter, ForReactNative, ForWeb and ForRen'Py; ForWgpu does not draw a Nines part at all yet, so it is a step behind rather than an exception.
  - **Not a per-part transform override.** Size is an authored *attribute* — `AttributeSizeX` / `AttributeSizeY`, decoded per keyframe and mixed like any other continuous attribute (`MIX_SIZE_X`, folded by `mix_tracks`) — which the Brain then turns into geometry. Overriding it says "this part was authored 200 px wide, make it 480" in the same voice as "this part was authored red, make it blue". A transform override would instead layer a matrix onto the resolved result, which is the thing that does not fit.
  - **The apply-seam is already in the right place.** `apply_part_overrides` writes into `resolved_layer.parts_vec` *before* `compose_frame_data` rebuilds the Nines geometry and before `resolve_global_state` computes the matrices — all three in that order inside `Context::get_frame_data` — so a size written there reaches the rebuilt 9-slice with no extra pass and no new plumbing. The vertex count changing with the size (tile fill mode repeats the middle slice) costs nothing either: `compose_frame_data` rebuilds those buffers and their per-part offsets every frame regardless.
  - **It cascades to children, and that is the point — but it has to be stated.** `compute_world_matrix` takes the parent's `(size_x, size_y)` as `parent_size` (`src/core/matrix.rs`), which is how SpriteStudio anchors a child inside its parent's box, so a label anchored in a stretched panel moves with the panel. That makes this the **one override that is not leaf-local**: the rest overwrite a part and stop there. Decide before building whether a host can opt out of the cascade, and document it either way.
  - **Open — which part kinds accept it.** Nines is the case that motivates it, Shape reads the same fields to build its vertices (`compute_shape_vertices`, `src/lib.rs`), and a Normal part's size drives its quad. "Any part with a size" is the cheap rule and "Nines only" the conservative one; pick one rather than letting it fall out of the implementation. The priority modes (`OverwriteOnNextKeyframe` / `HoldUntilNextAnimation` / `Permanent`) carry over unchanged, and there is **no `DrawBatch` design risk** of the cell override's kind — a size change cannot move a part between atlases, so split points are untouched.
- [ ] **Per-part masks for mixing** — an explicit per-track part mask. A track already reaches only as far as its animation keys, which covers overlays authored for the purpose (upper-body aim, damage reactions); a mask is what densely-keyed existing assets need to be layered without re-authoring.
- [ ] **Instance Lifecycle API** — one cohesive surface covering both:
  - Animation Instancing: shared evaluation context for driving many instances of the same animation, consumable by Players (e.g., crowd-style rendering).
  - Dynamic instance swap: runtime replacement of the animation mounted on an Instance part (equivalent to legacy `AnimationChangeInstance`). Must remain compatible with the shared-context semantics above.
  - **Co-decided**: a shared resource registry that holds several SSABs at once (resolve an animation by its pack hash across all loaded SSABs), used by Dynamic instance swap, External Instance resolution, and Sequence (`.ssqb`) items that reference another SSAB — one mechanism, not three. The host pre-registers the needed SSABs up front rather than the runtime calling back during `update()`, so all asset loading stays host-side and the Wasm/C# bindings need no FFI callbacks.
  - **Build order**: the shared resource registry is the keystone the other two wait on. A `Context` binds exactly one SSAB (`bind_resource` *replaces* it), and the pack-hash identifiers the format already carries (`PartTypeInstance.ref_anime_pack_hash`, `ExternalInstance.anime_pack_name_hash`) are not read, so there is no cross-SSAB resolution for the other two to stand on. Registry first, then swap and instancing on top of it. Dynamic swap starts from a primitive that already works: the host owns each child `Context` via `InstanceSlot` and can re-point it with `bind_resource` + `setup_animation` — what it lacks is a swap entry point and pack-hash target resolution.
- [ ] **State machine implementation** — runtime-side animation state graph (states + transitions) built on the mixing/crossfade primitives. Covers:
  - Game-driven transitions: states switched at runtime by Player-supplied triggers/conditions.
  - Reserved transitions (Spine's `addAnimation` + `delay`, Unity's exit time) — queueing a follow-on animation at authoring time rather than at the moment of the switch. Looked at during Animation Mixing and deliberately not built there: nothing outside a state graph needs it.
  - Sequence (`.ssqb`) playback: SpriteStudio-authored playlists run as a linear, auto-advancing configuration of the state graph (each item = a state; `repeat_count` = times to play before advancing; `SequenceType` Last/Keep/Top = end-of-list behavior). Reuses `set_loop_count` / `crossfade`, reproduces SS-editor semantics, and needs no `.fbs` change. Items referencing another SSAB (`ref_anime_pack`) resolve via the shared registry above and switch with no crossfade (blending is single-SSAB only). Built into the state graph, not a separate playback system.
  - **Depends on**: the mixing/crossfade primitives it drives (`crossfade` / `set_track_animation` / `add_track_source` / `set_loop_count` / `reset`, complete and surfaced over FFI and WASM) and the `.ssqb` data layer (parsed and converted end-to-end — `libs/sspj/src/ssqe.rs` → `libs/ssab/fbs/ssqb.fbs` → the ssqb converter, with fixtures). Both are in place, so what this item adds is runtime orchestration only. Items referencing another SSAB additionally wait on the Instance Lifecycle shared registry above.

## Backlog

*(Not scheduled into a phase. Worth doing, but each is either blocked on something outside this repo or small enough to pick up whenever it is convenient. Distinct from [Items not on the roadmap by design](#items-not-on-the-roadmap-by-design), which are decisions not to do the work at all.)*

- [ ] **Contributor License Agreement (CLA) / DCO integration** — Establish a formal process (e.g., via CLA assistant or DCO GitHub App) for contributors to agree to the project's licensing terms upon submitting Pull Requests, ensuring long-term IP protection.
- [ ] **tvOS / visionOS XCFramework slices** — extend the iOS XCFramework to also carry tvOS (`aarch64-apple-tvos` and the arm64 simulator) and visionOS (`aarch64-apple-visionos` and the arm64 simulator) slices in the same `libssruntime.xcframework`, with per-platform `Info.plist` (`CFBundleSupportedPlatforms` / `MinimumOSVersion` / `UIDeviceFamily`). The stable toolchain ships a prebuilt `std` for these targets, so this is a straightforward extension of `scripts/release-ios-xcframework.sh`; `x86_64-apple-tvos` has none, so the tvOS simulator slice is arm64 only. On the Player side tvOS reuses the iOS Swift/Metal path, and visionOS ships as a 2D-window app first, with true spatial (RealityKit) as separate later work.
- [ ] **Settle the `priority` type across the schemas** — One concept is declared three ways: keyframes are integers (`priority_array: [PartAnimationDataIntValue]`, `libs/ssab/fbs/ssab.fbs`), the initial attribute is a float (`ssab.fbs`), and the Player-facing resolved value is a float (`PartState.priority`, `libs/ssruntime/fbs/framedata.fbs`), with `val as f32` bridging them where `priority_array` is evaluated in `libs/ssruntime/src/core/framedata.rs`. **There is no live defect**: priority is authored as a small integer, which `f32` represents exactly, so the draw-order sort (`libs/ssruntime/src/core/z_order.rs`) orders identically to an integer comparison. What the float type does cost is a total ordering forced through a partial one in that comparator (`partial_cmp(..).unwrap_or(Equal)`), and a Player-facing surface that implies fractional priorities mean something when the data cannot carry them — an invitation to interpolate draw order linearly, which no keyframe authors. So the work is a decision, not a patch, and each direction has a price: integer end-to-end touches `PartState`, which is a **struct** where `int` and `float` are both 4 bytes — the layout survives, so an un-regenerated Player silently reinterprets the bits rather than failing to build; float keyframes would legitimise interpolating priority; documenting the resolved value as a deliberate widening leaves every site where it is. Pick one and record it. (Unrelated despite the name: `EffectParticleElementBasic.priority` in `ssab.fbs` is an emitter-side concept.)
- [ ] **Report `name_hash` collisions at convert time** — Hash-only references — `ref_anime_name_hash`, `start_label_hash`, cell / cellmap / sound names — resolve by comparing FNV-1a 32-bit hashes (`libs/ssconverter/src/utils.rs`), and a Player hashes host-supplied strings the same way at runtime (`ss_runtime_hash_string`), so two colliding names in one resolution scope silently play or draw the wrong thing with nothing in the toolchain able to point at the cause. Detection is per-scope and local: each name table the converter already builds — animations in a pack, labels in an animation, cells in a cellmap, cellmaps in a pack, sounds in a sound list, sequences in a `.ssqb` — inserts into a `HashMap<u32, &str>` and reports when an occupied slot holds a different name. There is no cross-file or global state, so scope-awareness is what keeps this small rather than what makes it hard. The probability is low (~1e-6 for a 100-name scope, ~1e-4 for 1,000), so the value is not preventing a likely defect but turning an undiagnosable runtime one into a build-time message. Emit it as a **warning**: an error would fail conversions that pass today. The converter already carries one guard of this class — `fnv1a_hash_texture_name` maps the authored "no override" to `0` because the FNV offset basis is indistinguishable from a real texture name — and this belongs beside it.
- [ ] **Close the coverage gap the fixtures and the test suite leave between them** — Defects keep surviving CI and being found by hand, and they land in two distinct blind spots. **Fixtures that do not author everything**: `tests/overall/Shape.ssae` authors only `rectangle`, so no other `ShapeType` is exercised by CI or by any Player — each authored enum / attribute wants a case. **Tests that do not drive the API the way a Player does**: `Instance.ssae` *does* author `INDEP_REVERSE` and `INDEP_PINGPONG`, but nothing stepped an Instance slot through them, so `child_looped` misfired on ~99% of ticks (#311); and nothing modelled a host writing the frame the runtime just reported back through `set_frame_no` — the loop Unity runs for independent children, and the one a clamp froze (#312). Unit tests that call the Brain the way a unit test finds convenient cannot see either. Worth attacking from both ends; the payoff is shared, since all seven Players inherit whatever the fixtures fail to exercise.
- [ ] **App Store validation of the iOS XCFramework** — the `.framework`-wrapped slices built by `scripts/release-ios-xcframework.sh` have not been through an end-to-end App Store archive and submission. Blocked on: a real device release.

## Design notes: Override / Mixing / State machine

These three runtime features — the **Override Layer API**, **Animation Mixing** and the **State machine** — all live *inside* the `FrameData` / `DrawBatch` boundary and attach at different stages of one evaluation pipeline. Per-feature behaviour is in the Player Porting Guide and what is still open is in the items above; the cross-cutting picture is here.

**Shared invariant.** All three change only the values that flow across the `FrameData` / `DrawBatch` boundary, never the schema. A single resolved `FrameData` is still emitted each frame, so every Player follows along with **no rendering-code change**, and each feature can ship on its own.

**Where each attaches in the pipeline** (`get_frame_data`): per-source keyframe decode → **weighted mix** of sources → **override overwrite** → emit. They share the per-part resolved-pose plumbing (the `resolved_layer` / part-index model and the apply-seam), **not one merge operation** — weighted blend and priority overwrite are different operations kept at different stages.

- **Mixing / Crossfade** is the weighted-composition stage: several sources resolved into one pose — continuous attributes mix by weight within a track and by the track's `alpha` between tracks, while discrete attributes (visibility, cell) come verbatim from track 0. The "Per-part masks for mixing" item **extends this stage** with an explicit per-track mask; it is not a separate mechanism. *Open questions*: **how sources of different lengths relate** — each `SourceState` owns its own `PlaybackController`, so a 30-frame walk and a 60-frame run currently run on independent clocks and drift apart; whether they should instead share a normalised phase is the decision the rest hangs off (it also decides whether a per-source "looped" could mean anything). The discrete-attribute rule needs designer confirmation too (see *Discrete-attribute resolution through the mix*).
- **Override Layer** is a distinct **post-mix overwrite**, *not* a source in the mix: it runs on the already-resolved pose and **wins over both keyframe and blend** — an imperative "make this part this color / cell / hidden now." Because its semantics are priority/overwrite (not weighted), it is deliberately its own pass rather than folded into the weighted mix. The **Per-part size override** item extends this same stage and is the one entry that breaks its leaf-local reading: a part's size feeds its children's world matrices, so that override reaches further down the hierarchy than the part it names.
- **State machine** sits on top of both — a transition graph (states + parameter / trigger / time conditions) that drives the **mixing weights** over time (and may also set overrides). Its evaluation reaches the output only through those weights / overrides; state-transition events ride the existing user-data / event path. Its data layer (`.ssqb`) is in place; what is open is the runtime orchestration — see *State machine implementation*.

Because none of them breaks the `FrameData` / `DrawBatch` contract, each ships independently with no Player changes.

## Items not on the roadmap by design

- **Text drawing** — a **Player responsibility**, not an SDK deliverable. Glyphs need host resources the Brain does not own: an outline font (`text_bitmap == 0`) is named by family only, so the font file is never in the `.ssab` and rasterising it needs the host's font stack; a bitmap font is already rasterised at conversion time and its atlas ships in the `.ssab` (`FontBitmap` / `FontGlyphBitmap`), leaving only layout, which every engine's text stack already does. Splitting the two by font type would put half a feature in the Brain for content that barely uses it, so both are Player-side. The Brain still reserves the part's place in the plan — a geometry-less `DrawBatchKind::Text` batch per text part — because priority resolution is not reproducible outside the runtime and a Player could otherwise never composite text correctly. Text authored as a mask is dropped from the plan instead: there are no glyphs to write coverage with. See [Limitations](./libs/ssruntime/docs/10_introduction/20_limitations.md).
- **Mask rendering / per-part mask evaluation** — a **Player responsibility**, not an SDK deliverable. The Brain only emits the cross-engine data — `DrawBatchKind::Mask` batches, `mask_indices`, and the `mask_influence` flag in the DrawBatch plan, plus the static PartData mask flags (`mask_write` / `visible_inside_mask` / `draw_as_mask`) and the per-frame `mask` value — all of which are part of the DrawBatch contract. Stencil/coverage rasterisation and clipping live in each Player (GPU stencil, or the coverage-bitmap hybrid where stencil is unavailable); see the Player guide [40_mask.md](./libs/ssruntime/docs/40_parts/40_mask.md).
- **Per-part AABB in FrameData** — a Player can derive it from vertex positions; revisit only on concrete Player-side demand.
- **Particle generation cap / runtime LOD** — a Brain-side upper bound that thins particles below the authored maximum. Effect playback is fast enough on the Player side that no cap is needed, so this item is not pursued. It is not a safety valve either: particle counts are already bounded per-emitter by the authored `maximum_particle` (`emitmax`) and generation is deterministic (seeded PRNG), so there is no runaway to guard against. Dynamic budgeting largely overlaps with instance-level culling, which is a **Player responsibility** (the Player knows device tier and frame budget). Revisit only on concrete demand — specifically a memory-fixed `no_std` target (console/embedded) where per-emitter × per-instance pre-allocation blows a fixed budget, or a dense single-emitter case that instance culling cannot address.
- **Flip override and vertex correction** — expressible as Player post-processing of FrameData (scale negation / UV swap); deliberately kept out of the Override Layer API. Covers legacy `FlipSetParts`.
- **Runtime texture / cell-map (atlas) swap** — a **Player responsibility**, not part of the Override Layer API. The Brain emits `DrawBatch.texture_hash`; Players already swap the bound texture by keying on it — see the Player guide [30_external_resources.md](./libs/ssruntime/docs/50_features/30_external_resources.md). A layout-changing atlas is served by a cell-reference override or by re-binding a different `.ssab`. (Distinct from the per-part authored `TextureChange` / `TCHG` attribute, which the runtime evaluates into `PartState.texture` **and folds into `DrawBatch.texture_hash`** so overridden parts split into their own batches — Players that bind by `texture_hash` need no per-part TCHG handling, but must resolve `external_textures` names in addition to cellmap names.)
- **Per-source playback flags** — `just_looped` / `is_finished` per blend source. Reporting the **primary** source only *is* the contract: a blend is one animation as far as the host is concerned, and the primary defines its cycle. The adjacent question — whose *events* fire — is separately answered and shipped: `update` walks every source, gates on `source_weight >= event_threshold` (default `1.0`, i.e. primary only), and tags each event with its `source_handle`, so a host that wants a secondary's events opts in per source. The flags would be near-free to add (every `SourceState` already owns a `PlaybackController` that tracks them), and that is not a reason to; what "looped" even means per source depends on how sources of different lengths relate (see the Design notes).
- **Instance-child playback flags** — `finished` for the animation on an Instance part. The **independent** child's finish is already observable — `ss_instance_slot_step` advances it through `child_ctx.update`, so the host reads `ss_runtime_is_finished(child_ctx)` on the child's own context; see [Instance parts](./libs/ssruntime/docs/40_parts/50_instance.md). Only the **synced** child lacks one, and neither does the C++ SDK: `SsAnimeDecoder::updateInstance` computes the same predicate and discards it, so upstream "finished" means only "pinned to the last frame" — which this runtime already reproduces. No signal to port, no consumer asking.
- **Force-visible override and an "all parts" setter sentinel** — a force-visible override, the mirror of force-hide, would beat a keyframed `hide`; it waits for a concrete need. A host that wants one call for every part loops. Cell overrides address cells by name hash only, matching the format; resolving an index to a hash is the host's job.
- **Per-part transform override** — a node transform layered onto the resolved pose does not fit this architecture. Per-part *size* is a different thing (an authored attribute) and is tracked as *Per-part size override*; whole-object colour and opacity are Player-side.
- **Additive mixing is a uniform delta against the setup pose** — no per-attribute rules, so `scale` and `alpha` are not special, and additive needs no "which frame is neutral?" parameter (the reference is the setup pose the converter writes to `parts_initial_attributes`). Kept because mix cannot express holding an overlay still on a playing base: mix damps the base's own motion by exactly its alpha.
- **Rotation mixes as raw degrees, and a sign-crossing `scale` lerps through zero** — a part at +131° in one source and −142° in the other travels the long arc; a part one source mirrors and the other does not vanishes at `alpha = 0.5`. Left as is: a mirrored part is a different pose rather than a pose with an in-between, and every alternative invents a rule the author did not ask for. Shortest-arc rotation (Spine's `shortestRotation`) would need a default.
