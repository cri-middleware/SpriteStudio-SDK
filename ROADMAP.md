# SpriteStudio-SDK Roadmap

Each item below states a **primary deliverable**. A few entries also list **Co-decided** sub-bullets — those are design points settled as part of the parent work so adjacent API contracts stay consistent. They are not separate tasks and should not be split into independent issues.

## Phase 1: Core Architecture & API Stabilization (Pre-Release)

*   [x] Restructure and improve Player Implementation Documentation.
*   [x] Add SSAB and FrameData schema documentation.
*   [x] Web (WASM) support for direct JS/TS usage via `wasm-pack`.
*   [x] Support for `no_std` environments (embedded/bare-metal).
*   [x] `DrawBatch` contract for cross-engine batched rendering (Brain-side batch emission with Mask batches and `mask_indices`).
*   [x] Particle quad emission and effect events surfaced via FrameData / FFI.
*   [x] Mesh part (`PartTypeMesh`) / Deform attribute (`PartAttributeDeform`) runtime evaluation.
*   [x] SSPlayer for Godot integration (serves as both C-API validation and Player migration).

## Phase 2: Ecosystem & Integration

*   [x] Migration of existing Players (Unity, pixi.js, etc.) to use `ssruntime`. The Unity, Web (pixi.js), and Ren'Py Players are all ssruntime-native — each is a thin "Body" driving the Rust "Brain" over FFI/WASM (`.ssab` input, DrawBatch/FrameData rendering), with no legacy playback or interpolation path remaining.
*   [x] **Override Layer API**: one cohesive per-part runtime override surface covering color, cell reference, and visibility — a port of the SS6PlayerForUnity per-part customization API, reconciled against what the SS7 SDK already provides. FFI/state only; no `.fbs` change. Prerequisite for migrating existing Players that depend on `PartsColorChange` / `CellChangeParts` / `HideSet`-equivalent semantics. Begin design during Phase 1's Godot integration so the C-API surface is validated on a fresh Player first. Roadmap-level scope and intent only — concrete API and design (apply-seam, priority modes, sRGB, FFI surface, validation plan) are worked out at implementation time and belong with the code, not in this roadmap:
    *   **Scope — three per-part overrides**: color / cell / visibility. The larger SS6 customization surface is deliberately out — either already provided (texture/cellmap swap), Player-side by design (flip, whole-object color/opacity), owned by another item (instance swap → Phase 3 *Instance Lifecycle API*), or not applicable to this architecture (per-part transform).
    *   **Design intent — build with Phase 3 in mind**: override is a *post-mix overwrite* that wins over the weighted mix, so it is its own pass — not part of the blend, and not a composition primitive that Mixing reuses. What Phase 3 shares is the **per-part addressing + apply-seam plumbing** (`resolved_layer` / part-index), which Phase 3 per-part blending also needs; build that infrastructure cleanly. See the [Design notes](#design-notes-override--mixing--state-machine) below.
    *   **Considered and left out** (so they are not re-proposed): a **force-visible** override, the mirror of force-hide, which would beat a keyframed `hide` — SS6 had none either, so it waits for a concrete need; and an **"all parts" sentinel** for the setter calls (SS6's `idParts == -1`), which a host can express by looping. Cell overrides address cells **by name hash only**, matching the format — the index-based form SS6 used is the host's to resolve. Behaviour and API are documented for Players in `libs/ssruntime/docs/40_components/65_override_layer.md`; the implementation is `libs/ssruntime/src/core/override_layer.rs`.
*   [x] **iOS dynamic XCFramework — `.framework`-wrapped slices**. The dynamic iOS XCFramework's slices now ship as proper iOS (flat) `libssruntime.framework` bundles — binary + `Headers/` + `Modules/module.modulemap` + `Info.plist` (`CFBundlePackageType=FMWK`), `install_name` `@rpath/libssruntime.framework/libssruntime`, and `MinimumOSVersion` pinned to the build's `IPHONEOS_DEPLOYMENT_TARGET` so the device slice's `LC_BUILD_VERSION` minos matches — for App Store-valid embedding (`scripts/release-ios-xcframework.sh` now uses `xcodebuild -create-xcframework -framework …`). The static (`.a`) XCFramework is unchanged; Unity and Godot keep static-linking `libssruntime.a`. The **Ren'Py Player** (the dynamic consumer that motivated this) consumes it via *Embed & Sign*, and its `deploy-ios.sh` guard/docs were updated to match. End-to-end App Store archive/submission validation is left to a real device release.

## Phase 3: Feature Expansion (Post-Release)

*(Phase 3 is post-release work, implemented without `.fbs` schema changes — additions go to FFI APIs and runtime state only; any item that turns out to need a schema change is reconsidered for an earlier phase.)*

*   [x] Animation Mixing in `ssruntime` — a track stack: tracks fold onto the setup pose in order, each with its own `alpha` and an interpolative or additive operator; several animations can share a track and mix by weight. Behaviour and API are documented for Players in `libs/ssruntime/docs/40_components/60_animation_mixing.{md,ja.md}`; the implementation is `mix_tracks` in `libs/ssruntime/src/lib.rs`.
    *   **Decided, so it is not re-proposed**: additive applies a **uniform delta against the setup pose** — no per-attribute rules, so `scale` and `alpha` are not special (`src/lib.rs:1214`). The reference is the setup pose the converter already writes to `parts_initial_attributes`, which is why additive needs no "which frame is neutral?" parameter. Additive was kept because mix cannot express what it does: holding an overlay still on a playing base at `alpha = 0.5`, the base's own motion survives at **49.6%** under mix (a lerp toward a static pose damps by exactly its alpha) against **106%** under additive.
    *   **Known and left alone — both look like the dipping the coverage rule exists to prevent, and are not it.** (i) **Rotation mixes as raw degrees**, so a part at +131° in one source and −142° in the other travels the 273° arc rather than the 87° one; **264 of 552** `Ringo` animation pairs swing some part ≥0.5× the character's own spread off the direct path (worst 1.16×). Spine's `shortestRotation` is the fix if one is wanted; it needs a default. (ii) **Sign-crossing `scale`** — a part one source mirrors and the other does not is lerped through **zero**, vanishing at `alpha = 0.5`; **85 of 552** `Ringo` pairs do this, every pair involving `dead` among them. Left as is: a mirrored part is a different pose, not a pose with an in-between, and every alternative invents a rule the author did not ask for.
    *   **Still open**, in the order they are likely to matter: **discrete-attribute resolution** through the mix (topmost covering track above a threshold, modelled on Spine's `mixAttachmentThreshold`) — specified but unbuilt, because cell switching goes through the Override Layer, and it must re-evaluate `DrawBatch` split points *after* the mix; **per-source playback control** (`play`/`pause`/`loop`/`is_finished` are track-0-only, while secondaries have frame/speed/weight — Vtuber-style overlay tracks want their own loop control); **crossfade interruption**, which today discards a running fade and restarts from `(1, 0)`, leaving abandoned sources at whatever weight they held (Spine keeps a `mixingFrom` chain instead — define a cleanup rule before considering one); and the **event-threshold default**, `1.0` here against Spine's `0`, which wants revisiting now that "primary" has weakened into "track 0".
*   [ ] Per-part masks for mixing — an explicit per-track part mask. A track already reaches only as far as its animation keys, which covers overlays authored for the purpose (upper-body aim, damage reactions); a mask is what densely-keyed existing assets need to be layered without re-authoring.
*   [ ] Instance Lifecycle API — one cohesive surface covering both:
    *   Animation Instancing: shared evaluation context for driving many instances of the same animation, consumable by Players (e.g., crowd-style rendering).
    *   Dynamic instance swap: runtime replacement of the animation mounted on an Instance part (equivalent to legacy `AnimationChangeInstance`). Must remain compatible with the shared-context semantics above.
    *   **Co-decided**: a shared resource registry that holds several SSABs at once (resolve an animation by its pack hash across all loaded SSABs), used by Dynamic instance swap, External Instance resolution, and Sequence (`.ssqb`) items that reference another SSAB — one mechanism, not three. The host pre-registers the needed SSABs up front rather than the runtime calling back during `update()`, so all asset loading stays host-side and the Wasm/C# bindings need no FFI callbacks.
    *   **Build order**: the shared resource registry is the keystone the other two wait on. A `Context` binds exactly one SSAB (`bind_resource` *replaces* it), and the pack-hash identifiers the format already carries (`PartTypeInstance.ref_anime_pack_hash`, `ExternalInstance.anime_pack_name_hash`) are not read, so there is no cross-SSAB resolution for the other two to stand on. Registry first, then swap and instancing on top of it. Dynamic swap starts from a primitive that already works: the host owns each child `Context` via `InstanceSlot` and can re-point it with `bind_resource` + `setup_animation` — what it lacks is a swap entry point and pack-hash target resolution.
*   [ ] State machine implementation — runtime-side animation state graph (states + transitions) built on the mixing/crossfade primitives. Covers:
    *   Game-driven transitions: states switched at runtime by Player-supplied triggers/conditions.
    *   Reserved transitions (Spine's `addAnimation` + `delay`, Unity's exit time) — queueing a follow-on animation at authoring time rather than at the moment of the switch. Looked at during Animation Mixing and deliberately not built there: nothing outside a state graph needs it.
    *   Sequence (`.ssqb`) playback: SpriteStudio-authored playlists run as a linear, auto-advancing configuration of the state graph (each item = a state; `repeat_count` = times to play before advancing; `SequenceType` Last/Keep/Top = end-of-list behavior). Reuses `set_loop` / `crossfade`, reproduces SS-editor semantics, and needs no `.fbs` change. Items referencing another SSAB (`ref_anime_pack`) resolve via the shared registry above and switch with no crossfade (blending is single-SSAB only). Built into the state graph, not a separate playback system.
    *   **Depends on**: the mixing/crossfade primitives it drives (`crossfade` / `set_track_animation` / `track_add_source` / `set_loop` / `reset`, complete and surfaced over FFI and WASM) and the `.ssqb` data layer (parsed and converted end-to-end — `libs/sspj/src/ssqe.rs` → `libs/ssab/fbs/ssqb.fbs` → the ssqb converter, with fixtures). Both are in place, so what this item adds is runtime orchestration only. Items referencing another SSAB additionally wait on the Instance Lifecycle shared registry above.
*   [ ] **`ssplayer-wgpu`** — the Rust-native Player, and the base the Rust ecosystem (Bevy and the like) builds on. It carries the same three-faced surface as `ssruntime` itself (Rust `rlib`, C via cbindgen, JS via wasm-bindgen), and doubles as the reference the other Players are read against. Developed in its own repository, [cri-middleware/SSPlayerForWgpu](https://github.com/cri-middleware/SSPlayerForWgpu), which consumes this one as a submodule: alone among the Players it links `ssruntime` and `ssab` as Rust crates instead of through the C-API, so `.ssab` and Rust-API changes reach it before they reach anything else.

## Backlog

*(Not scheduled into a phase. Worth doing, but each is either blocked on something outside this repo or small enough to pick up whenever it is convenient. Distinct from [Items not on the roadmap by design](#items-not-on-the-roadmap-by-design), which are decisions not to do the work at all.)*

*   **Contributor License Agreement (CLA) / DCO integration**: Establish a formal process (e.g., via CLA assistant or DCO GitHub App) for contributors to agree to the project's licensing terms upon submitting Pull Requests, ensuring long-term IP protection.
*   **tvOS / visionOS XCFramework slices**. Extend the iOS XCFramework to also carry tvOS (`aarch64-apple-tvos` + arm64/x86_64 simulator) and visionOS (`aarch64-apple-visionos` + arm64 simulator) slices in the same `libssruntime.xcframework`, with per-platform `Info.plist` (`CFBundleSupportedPlatforms` / `MinimumOSVersion` / `UIDeviceFamily`). **Deferred until these Rust targets reach Tier 2.** They are currently Tier 3 — rustup ships no precompiled `std`, so building them requires `-Z build-std` on **nightly**, which we do not want in the release toolchain. Because `ssruntime` is `no_std`, only `core`+`alloc` compile from source, so the work itself is small and was **proven feasible** (a local nightly + `build-std` build produced valid device/simulator slices whose binary `LC_BUILD_VERSION` minos matched the framework `MinimumOSVersion`); once the targets are Tier 2 (stable + prebuilt `std`), this becomes a straightforward extension of `scripts/release-ios-xcframework.sh` with no nightly dependency. Player-side (Body): tvOS reuses the iOS Swift/Metal path; visionOS ships as a 2D-window app initially, with true spatial (RealityKit) as separate later work.
*   **Settle the `priority` type across the schemas**. One concept is declared three ways: keyframes are integers (`priority_array: [PartAnimationDataIntValue]`, `libs/ssab/fbs/ssab.fbs:779`), the initial attribute is a float (`ssab.fbs:527`), and the Player-facing resolved value is a float (`PartState.priority`, `libs/ssruntime/fbs/framedata.fbs:137`), with `val as f32` bridging them at `libs/ssruntime/src/core/framedata.rs:661`. **There is no live defect**: priority is authored as a small integer, which `f32` represents exactly, so the draw-order sort (`libs/ssruntime/src/core/z_order.rs:59`) orders identically to an integer comparison. What the float type does cost is a total ordering forced through a partial one in that comparator (`partial_cmp(..).unwrap_or(Equal)`), and a Player-facing surface that implies fractional priorities mean something when the data cannot carry them — an invitation to interpolate draw order linearly, which no keyframe authors. So the work is a decision, not a patch, and each direction has a price: integer end-to-end touches `PartState`, which is a **struct** where `int` and `float` are both 4 bytes — the layout survives, so an un-regenerated Player silently reinterprets the bits rather than failing to build; float keyframes would legitimise interpolating priority; documenting the resolved value as a deliberate widening leaves every site where it is. Pick one and record it. (Unrelated despite the name: `EffectParticleElementBasic.priority` at `ssab.fbs:245` is an emitter-side concept.)
*   **Report `name_hash` collisions at convert time**. Hash-only references — `ref_anime_name_hash`, `start_label_hash`, cell / cellmap / sound names — resolve by comparing FNV-1a 32-bit hashes (`libs/ssconverter/src/utils.rs:19`), and a Player hashes host-supplied strings the same way at runtime (`ss_runtime_hash_string`), so two colliding names in one resolution scope silently play or draw the wrong thing with nothing in the toolchain able to point at the cause. Detection is per-scope and local: each name table the converter already builds — animations in a pack, labels in an animation, cells in a cellmap, cellmaps in a pack, sounds in a sound list, sequences in a `.ssqb` — inserts into a `HashMap<u32, &str>` and reports when an occupied slot holds a different name. There is no cross-file or global state, so scope-awareness is what keeps this small rather than what makes it hard. The probability is low (~1e-6 for a 100-name scope, ~1e-4 for 1,000), so the value is not preventing a likely defect but turning an undiagnosable runtime one into a build-time message. Emit it as a **warning**: an error would fail conversions that pass today. The converter already carries one guard of this class — `fnv1a_hash_texture_name` maps the authored "no override" to `0` because the FNV offset basis is indistinguishable from a real texture name — and this belongs beside it.
*   **Close the coverage gap the fixtures and the test suite leave between them**. Defects keep surviving CI and being found by hand, and they land in two distinct blind spots. **Fixtures that do not author everything**: `tests/overall/Shape.ssae` authors only `rectangle`, so no other `ShapeType` is exercised by CI or by any Player — each authored enum / attribute wants a case. **Tests that do not drive the API the way a Player does**: `Instance.ssae` *does* author `INDEP_REVERSE` and `INDEP_PINGPONG`, but nothing stepped an Instance slot through them, so `child_looped` misfired on ~99% of ticks (#311); and nothing modelled a host writing the frame the runtime just reported back through `set_frame_no` — the loop Unity runs for independent children, and the one a clamp froze (#312). Unit tests that call the Brain the way a unit test finds convenient cannot see either. Worth attacking from both ends; the payoff is shared, since all five Players inherit whatever the fixtures fail to exercise.

## Design notes: Override / Mixing / State machine

These three runtime features — the **Override Layer API** (Phase 2), **Animation Mixing** and the **State machine** (Phase 3) — all live *inside* the `FrameData` / `DrawBatch` boundary and attach at different stages of one evaluation pipeline. Per-feature scope lives in the items above; the cross-cutting picture is here.

**Shared invariant.** All three change only the values that flow across the `FrameData` / `DrawBatch` boundary, never the schema. A single resolved `FrameData` is still emitted each frame, so every Player follows along with **no rendering-code change**, and each feature can ship on its own.

**Where each attaches in the pipeline** (`get_frame_data`): per-source keyframe decode → **weighted mix** of sources → **override overwrite** → emit. They share the per-part resolved-pose plumbing (the `resolved_layer` / part-index model and the apply-seam), **not one merge operation** — weighted blend and priority overwrite are different operations kept at different stages.

*   **Mixing / Crossfade** is the weighted-composition stage: several sources resolved into one pose — continuous attributes mix by weight within a track and by the track's `alpha` between tracks, while discrete attributes (visibility, cell) come verbatim from track 0. The track stack shipped (`set_track_animation` / `set_track_alpha` / `set_track_blend` / `crossfade` / `fade_track` / `track_add_source`). The "Per-part masks for mixing" item **extends this stage** with an explicit per-track mask; it is not a separate mechanism. *Open questions*: **how sources of different lengths relate** — each `SourceState` owns its own `PlaybackController`, so a 30-frame walk and a 60-frame run currently run on independent clocks and drift apart; whether they should instead share a normalised phase is the decision the rest hangs off (it also decides whether a per-source "looped" could mean anything). Then parent/child ordering when composing across the bone hierarchy, and the discrete-attribute rule (all need designer confirmation).
*   **Override Layer** is a distinct **post-mix overwrite**, *not* a source in the mix: it runs on the already-resolved pose and **wins over both keyframe and blend** — an imperative "make this part this color / cell / hidden now." Because its semantics are priority/overwrite (not weighted), it is deliberately its own pass rather than folded into the weighted mix. *Design risk*: a cell override that crosses a texture-atlas boundary shifts `DrawBatch` split points, so the batch-merge condition must reflect the *post-override* cell (folded into the Brain's draw planning).
*   **State machine** sits on top of both — a transition graph (states + parameter / trigger / time conditions) that drives the **mixing weights** over time (and may also set overrides). Its evaluation reaches the output only through those weights / overrides; state-transition events ride the existing user-data / event path. *Sketch FFI*: `ss_runtime_sm_set_parameter` / `ss_runtime_sm_trigger` / `ss_runtime_sm_current_state`. Its largest external dependency is `.ssqb` schema design plus SpriteStudio-side authoring support — it does not stand alone in the runtime.

Because none of them breaks the `FrameData` / `DrawBatch` contract, each ships independently with no Player changes.

## Items not on the roadmap by design

*   Text drawing (a **Player responsibility**, not an SDK deliverable). Glyphs need host resources the Brain does not own: an outline font (`text_bitmap == 0`) is named by family only, so the font file is never in the `.ssab` and rasterising it needs the host's font stack; a bitmap font is already rasterised at conversion time and its atlas ships in the `.ssab` (`FontBitmap` / `FontGlyphBitmap`), leaving only layout, which every engine's text stack already does. Splitting the two by font type would put half a feature in the Brain for content that barely uses it, so both are Player-side. The Brain still reserves the part's place in the plan — a geometry-less `DrawBatchKind::Text` batch per text part — because priority resolution is not reproducible outside the runtime and a Player could otherwise never composite text correctly. Text authored as a mask is dropped from the plan instead: there are no glyphs to write coverage with. See [Limitations](./libs/ssruntime/docs/10_introduction/20_limitations.md). Decided 2026-07.
*   Mask rendering / per-part mask evaluation (a **Player responsibility**, not an SDK deliverable). The Brain only emits the cross-engine data — `DrawBatchKind::Mask` batches, `mask_indices`, and the `mask_influence` flag in the DrawBatch plan, plus the static PartData mask flags (`mask_write` / `visible_inside_mask` / `draw_as_mask`) and the per-frame `mask` value — all of which shipped with the Phase 1 DrawBatch contract. Stencil/coverage rasterisation and clipping live in each Player (GPU stencil, or the coverage-bitmap hybrid where stencil is unavailable); see the Player guide [09_mask.ja.md](./libs/ssruntime/docs/40_components/40_mask.ja.md). Already implemented in the Unity and Godot players.
*   Per-part AABB in FrameData (Player can derive from vertex positions; revisit only on concrete Player-side demand).
*   Particle generation cap / runtime LOD (a Brain-side upper bound that thins particles below the authored maximum). Effect playback is fast enough on the Player side that no cap is needed, so this item is not pursued. It is not a safety valve either: particle counts are already bounded per-emitter by the authored `maximum_particle` (`emitmax`) and generation is deterministic (seeded PRNG), so there is no runaway to guard against. Dynamic budgeting largely overlaps with instance-level culling, which is a **Player responsibility** (the Player knows device tier and frame budget). Revisit only on concrete demand — specifically a memory-fixed `no_std` target (console/embedded) where per-emitter × per-instance pre-allocation blows a fixed budget, or a dense single-emitter case that instance culling cannot address.
*   Flip override and vertex correction (expressible as Player post-processing of FrameData — scale negation / UV swap; deliberately kept out of the Override Layer API. Covers legacy `FlipSetParts`).
*   Runtime texture / cell-map (atlas) swap (a **Player responsibility**, not part of the Override Layer API). The Brain emits `DrawBatch.texture_hash`; Players already swap the bound texture by keying on it — see the Player guide [70_external_resources.ja.md](./libs/ssruntime/docs/40_components/70_external_resources.ja.md). This is the modern equivalent of SS6's cellmap-level `TextureSetCellMap`; SS6 had no *per-part* texture override. A layout-changing atlas is served by a cell-reference override or by re-binding a different `.ssab`. (Distinct from the per-part authored `TextureChange` / `TCHG` attribute, which the runtime evaluates into `PartState.texture` **and folds into `DrawBatch.texture_hash`** so overridden parts split into their own batches — Players that bind by `texture_hash` need no per-part TCHG handling, but must resolve `external_textures` names in addition to cellmap names.)
*   Per-source playback flags (`is_looped` / `is_finished` per blend source). Reporting the **primary** source only *is* the contract: a blend is one animation as far as the host is concerned, and the primary defines its cycle. The adjacent question — whose *events* fire — is separately answered and shipped: `update` walks every source, gates on `source_weight >= event_threshold` (default `1.0`, i.e. primary only), and tags each event with its `source_handle`, so a host that wants a secondary's events opts in per source. The flags would be near-free to add (every `SourceState` already owns a `PlaybackController` that tracks them), and that is not a reason to; what "looped" even means per source waits on the Mixing open question above. Decided 2026-07.
*   Instance-child playback flags (`finished` for the animation on an Instance part). The **independent** child's finish is already observable — `ss_instance_slot_step` advances it through `child_ctx.update`, so the host reads `ss_runtime_is_finished(child_ctx)` on the child's own context; see [Instance parts](./libs/ssruntime/docs/40_components/10_instance.ja.md). Only the **synced** child lacks one, and neither does the C++ SDK: `SsAnimeDecoder::updateInstance` computes the same predicate and discards it, so upstream "finished" means only "pinned to the last frame" — which this runtime already reproduces. No signal to port, no consumer asking. Investigated 2026-07.
